# Enterprise & compliance guide

`copilot-usage-tracker` is designed so a security review can say **yes**:
it is read-only, local-first, least-privilege, and policy-driven. This
guide is what you hand to IT, security, or the works council.

## The 30-second pitch for security review

- **Read-only against GitHub.** The tool only issues `GET`/`POST` (report
  request) calls to GitHub's usage and billing endpoints. It never writes
  to your org, repos, teams, or billing settings.
- **Local-first.** Everything lands in a SQLite file on the machine that
  runs the collector. The only network destinations are your GitHub API
  endpoint (or your GitHub Enterprise Server) — no third-party analytics,
  no telemetry, no phone-home.
- **Least privilege.** It needs a token that can *read* Copilot usage and
  billing data — nothing that can change code, settings, or membership.
  See "Token scopes" below.
- **Policy as code.** `policy.yaml` lets your company declare the rules:
  which scopes may be collected, whether per-user rows exist at all,
  whether identities are pseudonymized, how long data is kept, which
  proxy/CA to use. Generate one with
  `copilot-usage init-policy --preset strict`.
- **Audit trail.** Every API call is appended to `audit.jsonl`
  (timestamp, method, host, path, safe query params, status). Ship it to
  your SIEM to prove the tool stayed in its lane. Auth headers and signed
  download-URL tokens are never logged.

## Data flow

```
GitHub API (api.github.com or your GHES host)
   │  GET usage reports, billing usage, report exports (read-only)
   ▼
copilot-usage-tracker (this machine)
   │  SQLite: copilot_usage.db (or $COPILOT_DB)
   │  Audit:   ~/.copilot-usage-tracker/audit.jsonl
   ▼
Dashboard / CLI reports (this machine only)
```

Nothing leaves the machine except the GitHub API calls themselves.
Streamlit's usage telemetry is disabled (`--browser.gatherUsageStats false`
plus `STREAMLIT_BROWSER_GATHER_USAGE_STATS=false` in the tray app).

## Token handling: sourced, never stored

The tool resolves the GitHub token once per process (then reuses it from
memory for every API call) from the first source that has one:

1. `GITHUB_TOKEN` env var — CI / containers / secrets managers.
2. OS keyring (Windows Credential Manager, macOS Keychain, Linux Secret
   Service) — written only by `copilot-usage login` with your explicit
   consent; removed by `copilot-usage logout`.
3. `gh` CLI session (`gh auth token`) — reuses an existing login, so no
   new secret exists at all.
4. Interactive prompt (hidden input) — memory-only.

The tool itself **never writes the token anywhere**: not to
`policy.yaml`, not to SQLite, not to the audit log, not to any cache
file. It is excluded from `repr(Settings)` (no traceback leaks), shown
only masked (`ghp_…abcd`), and `copilot-usage auth` reports which source
is in play plus a live validation (`@user`, scopes).

```bash
copilot-usage login    # guided: validates, offers OS-keyring storage
copilot-usage auth     # source + masked token + live validation
copilot-usage logout   # removes the keyring token
```

## Token scopes (least privilege)

Create a token for a service account (not a human admin's PAT) with the
minimum needed for your scope:

- **Usage metrics reports**: enterprise/org owner, billing manager, or a
  custom role with **View Enterprise Copilot Metrics**.
- **AI-credit billing endpoint** (`/settings/billing/ai_credit/usage`):
  enterprise billing read access.
- **Billing reports export**: same billing read access.

The token needs **no** `repo`, `write:org`, or admin scopes. Authenticate
with `copilot-usage login` (guided; the token is never stored by the tool
itself — it lives in your OS keyring only if you opt in, otherwise in
`GITHUB_TOKEN` or your `gh` CLI session). Never put a token in
`policy.yaml` or the repo.

For GitHub Enterprise Server, point the tool at your host:

```bash
export COPILOT_API_BASE="https://ghe.example.com/api/v3"
# or set network.api_base in policy.yaml
```

## policy.yaml reference

```bash
copilot-usage init-policy --preset strict   # strict | standard | aggregate
```

| Section | Key | What it does |
|---|---|---|
| `collection` | `allowed_scopes` | Allowlist of enterprise/org logins that may be collected. Empty = only the configured `COPILOT_ENTERPRISE`/`COPILOT_ORG`. Anything else aborts. |
| `collection` | `collect_per_user` | `false` = aggregate mode: no per-user rows at all, only scope/team totals. |
| `privacy` | `anonymize_users` | Replace logins/ids with stable salted pseudonyms (`user_9f2ac41d…`) before storage. |
| `privacy` | `user_salt` | Salt for pseudonyms. Generated by `init-policy`; keep it stable or pseudonyms churn. Treat like a secret. |
| `privacy` | `retention_days` | Auto-purge rows older than N days after every `collect` (`0` = keep forever). Manual: `copilot-usage purge --days 90`. |
| `privacy` | `drop_raw_json` | Don't store raw NDJSON payloads in the DB. |
| `network` | `proxy` | Corporate proxy, e.g. `http://proxy.corp:8080` (else `HTTPS_PROXY` env is honored). |
| `network` | `ca_bundle` | Path to corporate CA bundle for TLS inspection proxies. |
| `network` | `api_base` | GHES API base URL. |
| `audit` | `enabled` / `path` | JSONL audit log of every API call. |

Every file value can be overridden by env vars for containers/CI:
`COPILOT_POLICY_FILE`, `COPILOT_ALLOWED_SCOPES`, `COPILOT_COLLECT_PER_USER`,
`COPILOT_ANONYMIZE_USERS`, `COPILOT_USER_SALT`, `COPILOT_RETENTION_DAYS`,
`COPILOT_DROP_RAW_JSON`, `COPILOT_PROXY`, `COPILOT_CA_BUNDLE`,
`COPILOT_API_BASE`, `COPILOT_AUDIT`.

## Presets

- **standard** — per-user collection, 1-year retention, audit on. For
  companies comfortable with named per-user FinOps data.
- **strict** — pseudonymized users, no raw payloads, 90-day retention,
  audit on. For GDPR / works-council environments (e.g. a Microsoft-style
  review): re-identification requires the salt, which stays with the data
  owner.
- **aggregate** — no per-user rows *at all*; team and scope totals only,
  180-day retention. When individual tracking is off the table entirely.

## Privacy notes (GDPR / works council)

- **Data minimization**: `aggregate` preset collects no personal data
  beyond what GitHub's team-level rollups already anonymize; `strict`
  keeps per-user rows but pseudonymized.
- **Purpose limitation**: the tool computes cost attribution and budgets —
  document that purpose next to the deployment, not the tool's job, but
  the audit log gives you the evidence of what was actually collected.
- **Right to erasure**: `copilot-usage purge --days N` deletes old rows;
  point retention at your policy and it's automatic.
- **No cross-border surprises**: data never leaves the machine you run it
  on; choose that machine's region and you're done.

## Adapting to a specific company's rules

1. Run `copilot-usage init-policy --preset strict` (or `aggregate`).
2. Fill in `allowed_scopes`, `network.proxy`/`ca_bundle` if behind a
   corporate proxy, and `network.api_base` for GHES.
3. Hand `docs/ENTERPRISE.md` + a sample `audit.jsonl` to the security
   review — the log is the proof of read-only, scoped behavior.
4. Deploy the collector on a schedule (cron / systemd timer) writing to a
   company-owned path via `COPILOT_DB`; keep `policy.yaml` and the salt
   with the data owner, not in git.
